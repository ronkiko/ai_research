# game2: управление в физическом мире

Независимое исследование платформера для локального обучаемого MLP. Цель —
научиться управлять телом во времени по семантическому изображению и
минимальной физической метаинформации. Текущая сеть `3-8-2` получает три
признака и выдаёт два решения.

По ощущению движения ориентируемся на Prince of Persia: разбег, инерция,
момент отрыва и баллистика. Это собственная упрощённая физика.

## Контейнер и компоненты

`GameContainer` в `game.py` — единственная точка сборки и владелец жизненного
цикла. Он загружает карту, создаёт физику, джойстик, рендер и мониторы, ведёт
такты/эпизоды, проверяет цель уровня, перезапускает попытку и освобождает ресурсы.
`engine.py` только разбирает CLI и запускает контейнер.

| Компонент | Файл | Ответственность |
|---|---|---|
| Контейнер | `game.py` | Сборка, цикл времени, эпизод, успех/смерть, reset/close |
| Физический движок | `physics.py` | Тело, ускорения, инерция, гравитация, столкновения, damage |
| Загружаемая карта | `level.py`, `maps/*.json` | Сетка 64×64, старт, коллайдеры из клеток, цель |
| Общие действия | `controls.py` | Неизменяемый `Action(right, jump)` |
| Джойстик человека | `joysticks.py` | Клавиши → те же действия |
| Джойстик MLP | `mlp_joystick.py` | Команды сокета → действия на заданных тактах |
| Монитор датчиков | `monitors.py:ColorRenderer` | Четырёхцветный растр физической геометрии |
| Графический рендер | `tile_renderer.py:TileRenderer` | Фон, тайлы земли, декорации из ассетов |
| Монитор человека | `monitors.py:WindowMonitor` | Игровое окно и отдельный HUD |
| Монитор MLP | `monitors.py:MlpMonitor` | Поток цветовых кадров с номерами тактов |
| Сетевой транспорт | `socket_io.py` | TCP в отдельном потоке, ограниченные буферы |
| Протокол / клиент | `protocol.py`, `mlp_client.py` | Бинарный формат и адаптер для локального MLP |
| Pixel-сенсоры | `sensors.py` | Distance/grounded из растра, velocity metadata |
| Политика `3-8-2` | `mlp_382.py` | PyTorch MLP, REINFORCE и checkpoint |
| Запуск MLP | `mlp_runner.py` | Игровой цикл, планирование действий и эпизодная награда |

Физика не импортирует карту, Pygame, сеть или контейнер. Карта не исполняет код.
Джойстики не получают тело, карту или координаты; они формируют только действия.
Мониторы не меняют физику. Оба джойстика используют один `GameContainer.step`.
Одновременно активен один источник управления. В режиме MLP можно включить окно
наблюдателя, которое не перехватывает управление у MLP.

## Запуск человеком

Python 3.10+ и графический рабочий стол:

```bash
cd game2
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python engine.py
```

- **Right** — разгон на земле; отпускание — торможение.
- **Up** — однократный прыжок с земли.
- **R** — новая попытка; **Esc** или закрытие окна — выход.
- Потеря фокуса отпускает кнопки; автоповтор Up не создаёт новые прыжки.

Движения влево в игровых действиях пока нет. Физическое ядро поддерживает
направление −1/0/+1, но оба игровых джойстика имеют одинаковые Right/Up.

## Запуск для MLP: сокет и непрерывное время

```bash
python engine.py --mode mlp --port 8765
```

Для этого режима достаточно стандартной библиотеки Python, Pygame не нужен.
Сервер слушает `127.0.0.1:8765`, принимает один контроллер и поддерживает
переподключение. Для наблюдения за MLP в окне:

```bash
python engine.py --mode mlp --port 8765 --window
```

В окне наблюдателя работает только закрытие/Esc; Right/Up/R не управляют игрой.

## Подключение и обучение 3-8-2

Сначала запусти игру в одном терминале:

```bash
python engine.py --mode mlp --window
```

Затем в другом терминале запусти локальный обучаемый MLP:

```bash
python mlp_runner.py --mode train --episodes 1000
```

Для запуска окна и обучения одной командой используй:

```bash
./train.sh
```

Скрипт запускает окно и MLP параллельно. Закрытие окна завершает тренировку;
завершение или ошибка тренировки закрывает окно. По умолчанию выполняется 1000
эпизодов. Количество эпизодов и порт можно переопределить переменными
`EPISODES` и `PORT`.

Обычный запуск продолжает существующий checkpoint, а `FRESH=1` начинает новый
эксперимент без удаления старых весов. В начале запуска печатается
`training_mode=resume` или `training_mode=fresh`:

```bash
./train.sh
FRESH=1 ./train.sh
EPISODES=5000 FRESH=1 ./train.sh
```

Для ускоренного headless-обучения без Pygame-окна:

```bash
./train.sh auto
AUTO_SPEED=50 EPISODES=5000 ./train.sh auto
```

Auto сохраняет физику 120 Hz, observations 30 Hz и tick-based scheduling
команд. `AUTO_SPEED` задаёт только максимальный wall-clock pacing: если socket
или MLP не успевают, симуляция замедляется вместо пропуска ticks или команд.

`mlp_runner.py` подключается к TCP-сокету и получает изображения. Канонический
порядок входов MLP:

```text
(distance_to_gap, grounded, velocity_x)
                  ↓
                3-8-2
                  ↓
            (Right, Jump)
```

`distance_to_gap` показывает, насколько близко следующий обрыв, `grounded` —
есть ли сейчас опора и может ли физический Jump реально начаться, а
`velocity_x` — текущая горизонтальная скорость/разбег. Первые два признака
извлекаются из semantic pixel frame; скорость приходит из observation metadata
и берётся из `body.vx`, нормализованного на `PhysicsConfig.max_speed`.

Одинаковое расстояние до ямы при почти нулевой скорости и при полном разбеге —
разные физические состояния, которые старая `2-4-2` различить не могла.
`3-8-2` имеет два независимых выхода: один выбирает Right, второй — Jump.
Оба выхода выбираются MLP на каждом observation.

Поскольку правильный момент заранее не размечен, используется обучение с
подкреплением по результату эпизода: успешное приземление даёт `+1`, смерть или
тайм-аут дают `-1`. Веса обновляются после каждого пригодного для обучения эпизода методом REINFORCE.
Это отличается от построчного supervised-обучения `game1`: физическая среда
сообщает результат с задержкой и не выдаёт готовый target для каждого кадра.

Каждый terminal JSON также содержит rolling-метрики по последним 100 попыткам:
`success_rate_100`, `successes_100`, `episodes_window` и
`mean_terminal_tick_100`. `attempts`, `successes` и `success_rate_total` —
cumulative-счётчики. В окно попадают и смерть, и тайм-аут; `terminal tick` —
фактический tick завершения попытки. Эти метрики не влияют на обучение. `loss`
сам по себе не является метрикой качества политики.

Checkpoint сохраняется по умолчанию в `models/3-8-2/weights.pt`. Старые
checkpoint `2-4-2` несовместимы с новой моделью и не загружаются.
Повторный запуск `train` продолжает обучение с этого checkpoint; для нового эксперимента
используется `--fresh`. Запись checkpoint атомарная; версия 2 сохраняет также
состояние генератора случайных чисел. Старые checkpoint версии 1 загружаются,
но не содержат это состояние. Проверить текущие веса без обновления можно так:

```bash
python mlp_runner.py --mode play --episodes 20
```

Для отдельной проверки generalization на короткой карте используй тот же
checkpoint, но другой game process:

```bash
# terminal 1
python engine.py --mode mlp --map maps/short_pit.json --window

# terminal 2
python mlp_runner.py --mode play --episodes 100
```

Режим `play` только оценивает checkpoint: он не вызывает optimizer update и не
сохраняет веса. Он выводит те же rolling и cumulative success-метрики. Это
отдельная evaluation-серия на `short_pit.json`, а не продолжение обучения.

Параметры `--target-delay` и `--hold-ticks` задают планирование действий вперёд
по физическим тактам. По умолчанию команда планируется на 32 такта вперёд и
удерживается 48 тактов: это оставляет запас на задержку кадра и inference.
Runner не маскирует действия MLP. MLP может выбрать прыжок на месте, повторный
прыжок после приземления или управление Right в любой момент. Единственное
ограничение задаёт физика: Jump во время полёта не имеет эффекта, а после
приземления снова доступен. Окно нужно только для наблюдения за игрой и не
ограничивает пространство действий.
В observation protocol v3 есть нормализованный `velocity_x` и два диагностических
cumulative-счётчика:
`jump_requested` — Jump, дошедший до физического tick, и `jump_applied` — Jump,
для которого физика обнаружила опору и начала отрыв. Terminal JSON показывает
дельту этих счётчиков за попытку. Игнорированный в воздухе Jump не считается
реально применённым, но сам выбор MLP не скрывается.
Для REINFORCE сохраняется log-probability полного выбранного joint-action,
включая Jump, который физика проигнорировала. `jump_applied` используется для
диагностики, а не для action masking, выборочного удаления log-probability или
reward shaping.
Это не задерживает физику и не превращает сеть в часть движка: inference
остаётся отдельным процессом, связанным только протоколом.

Каждый запуск начинает чистую попытку через reset. В градиент входят только
решения, подтверждённые сокетом и достигшие своего target_tick до завершения
эпизода. Команды, оставшиеся в будущем, не получают награду за уже завершённую
игру. При опоздании/отклонении команд или внешнем reset весь эпизод исключается
из обновления: текущий протокол имеет накопительное подтверждение, поэтому
надёжно приписать награду отдельным отклонённым командам нельзя. Повторный кадр
с тем же tick не порождает ещё одну команду. Лог показывает `updated`,
`executed_actions`, `late`, `rejected`, `jump_requested` и `jump_applied`;
счётчик `episodes` в статистике политики
означает число обновлений, а не число всех попыток.

Три признака — упрощённое наблюдение, а не полное физическое состояние. В
протокол не передаются `x`, `y`, `vy`, карта, внутренние surfaces или прочее
состояние физики. `velocity_x` не вычисляется по истории кадров. Меняющиеся веса подтверждают выполнение обучения, но рост доли
успеха проверяется отдельно сериями запусков `play`, а не по одному loss.


**Игра не ждёт MLP.** Физика идёт с фиксированным шагом 1/120 s даже без
подключения. Монитор MLP отправляет кадры с целевой частотой 30 Hz. Окно
человека обновляется с целевой частотой 60 Hz. Это лабораторный real-time цикл,
а не гарантия hard real-time от ОС/Python. MLP работает вне контейнера.

Каждая команда задаёт:

- номер эпизода и уникальный возрастающий номер команды;
- будущий физический такт `target_tick`;
- кнопки `right`, `jump`;
- срок удержания `hold_ticks`: 1..120 физических тактов.

На `target_tick` команда заменяет удержание Right. Jump действует **только на
первом такте**, даже если удержание длится дольше. После срока Right отпускается.
Команда должна поступить до начала своего такта. Опоздавшие команды отклоняются
и учитываются в `late`; неверный эпизод, повторный номер и такт дальше чем на
120 от текущего — в `rejected`. Из команд на один такт используется последняя
принятая. Эти правила применяются к действиям, а не меняют dt физики.

При разрыве соединения накопленные действия и удержание сбрасываются при
ближайшем опросе джойстика. На земле тело тормозит физически, а не телепортируется
к остановке; в воздухе инерция сохраняется. Если контроллер завис, не закрыв
сокет, удержание закончится по `hold_ticks`.

`MLPClient` постоянно читает сокет в своём потоке и хранит только последнее
наблюдение: длительный inference не создаёт очередь старых кадров. Сетевой
транспорт игры также хранит один отправляемый и один последний ожидающий кадр;
частично отправленный пакет всегда заканчивается целиком. Медленный читатель,
заблокировавший отправку пакета больше 0,5 s, отключается. Очередь команд
ограничена 256 пакетами; переполнение и неверная длина пакета закрывают соединение.

## Подключение локального MLP

Пример одной команды (это демонстрация интерфейса, не обученный контроллер):

```python
from mlp_client import MLPClient

with MLPClient(port=8765) as joystick:
    observation = joystick.receive()
    # observation['pixels']: bytes, один цветовой индекс на пиксель.
    # Здесь датчики/сеть вычисляют нужное действие.
    joystick.action(
        episode=observation['episode'],
        target_tick=observation['tick'] + 8,
        hold_ticks=8,
        right=True,
        jump=False,
    )
    following = joystick.receive()
    # Принятие команды подтверждается following['accepted'].
    # Для новой попытки: joystick.reset(following['episode']).
```

В рабочем цикле MLP должен постоянно получать актуальные наблюдения и
обновлять команды. Запас +8 тактов — пример (около 67 ms), не гарантия для любой
скорости inference. `accepted` подтверждает приём, а не успешное исполнение
физического действия. Поздние команды видны по счётчику `late`. После reset нужно
дождаться кадра с новым `episode`, затем отправлять команды для него.

Полная спецификация байтов и порядок полей — в [PROTOCOL.md](PROTOCOL.md).
Через сокет не передаются JSON, пути файлов или Python-объекты. Публичный формат
может использовать адаптер MLP на другом языке.

## Карты

```bash
python engine.py --map maps/pit.json
python engine.py --map maps/short_pit.json
python engine.py --mode mlp --map maps/short_pit.json
```

Карты теперь используют **формат версии 2**, все размеры и позиции задаются
целыми клетками. Тайл исходного `FreeCuteTileset` — 16×16, масштаб ×4 без
сглаживания, один игровой блок — **64×64 px**. Игрок занимает один блок.

Стандартная яма в обеих демонстрационных картах: **4 блока шириной (256 px)**,
опасное дно на **3 блока ниже земли (192 px)**. Разница карт — длина разбега и
общая ширина, физика одна и та же.

| Карта | Сетка / изображение | Яма по столбцам | Земля / опасное дно |
|---|---|---|---|
| `pit.json` | 20×12 / 1280×768 | 8..11, x=512..768 | y=448 / 640 |
| `short_pit.json` | 16×12 / 1024×768 | 6..9, x=384..640 | y=448 / 640 |

Поля карты:

| Поле | Содержимое |
|---|---|
| `schema_version` | 2; старые пиксельные карты версии 1 нужно мигрировать |
| `name` | Название |
| `tile_size` | 64 — общий стандарт |
| `columns`, `rows` | Размер сетки, 2..64 клетки по каждой оси |
| `spawn`, `goal` | `column`, `row`, `columns`, `rows`, в клетках |
| `terrain` | Строки одинаковой длины: `.` пустота, `#` земля, `^` опасный блок |
| `decorations` | Объекты `sprite`, `column`, `baseline` |

`baseline` — линия низа декорации в клетках; `column` — её левый край.
Доступны `tree`, `bush`, `ruin` из `Decors.png`. Декорации не имеют коллайдеров
и не меняют наблюдение MLP. Неизвестные символы, спрайты, размеры и версии
отклоняются загрузчиком. Spawn и goal обязаны помещаться в карту.

Загрузчик объединяет горизонтальные ряды одинаковых клеток в прямоугольные
коллайдеры, затем передаёт их обычному `PhysicsWorld`. Геометрия карты существует
в одном месте — `terrain`; отдельного вручную поддерживаемого списка поверхностей
нет. Боковые границы и потолок создаются на внешней границе сетки. Опасное дно
задаётся видимыми клетками `^`, а не специальной логикой ямы в физике.

Успех: живой игрок стоит на опоре и полностью находится в `goal`.
Карта загружается при создании контейнера; reset использует ту же неизменяемую
карту. Для другого уровня передаётся другой файл `--map`, без правок движка.

### Три слоя окна

1. **Фон:** `BG1.png` (небо), `BG2.png` (горы), `BG3.png` (холмы), собранные
   в один задний слой по примеру `Mockup2x.png`.
2. **Земля:** тайлы травы, грунта и открытых боков из `Tileset.png`.
3. **Декорации:** деревья, кусты и руины из `Decors.png`.

Статические слои собираются один раз при открытии окна. Игрок рисуется поверх
них, HUD — ниже игрового поля. Все ассеты увеличиваются целочисленно ×4.
В наборе нет тайла шипов: опасные клетки показаны отдельной полосой шипов,
нарисованной рендером на той же сетке. Их физический объём — целая клетка `^`;
MLP видит весь этот объём красным. Исходные PNG не изменены.

После перехода на новую геометрию старые веса можно загрузить, но результат
нужно проверить заново: поменялись размеры карты и нормализованное расстояние
до ямы. Для отдельного обучения этой версии можно использовать `--fresh`.

## Физика

Прежняя проверенная баллистика сохранена:

- физика 120 Hz; гравитация 1800 px/s²;
- разгон 1800 px/s², максимум 340 px/s, торможение 1400 px/s²;
- вертикальная скорость отрыва 700 px/s;
- разгон/торможение только на земле, до отрыва;
- в полёте кнопки не меняют горизонтальную скорость;
- прыжок из покоя, включая первое одновременное Right+Up, вертикальный;
- повторный прыжок в воздухе и прыжок после схода с края запрещены;
- swept AABB предотвращает прохождение сквозь тонкие препятствия;
- потолок останавливает подъём, стена — горизонтальное движение;
- контакт с `damage=True` с любой стороны вызывает `die` ровно один раз.

Торможение с максимальной скорости: 30 тактов / 0,25 s / примерно 39,9 px.
Прыжок на ту же высоту: 93 такта / 0,775 s / примерно 263,5 px с полным разбегом.
Это одно прямоугольное тело и неподвижные прямоугольные поверхности. Склоны,
движущиеся платформы, вращение, хват за край и урон от скорости падения не входят
в текущую физику. Параметры задаются `PhysicsConfig`, независимо от файла карты.

## Наблюдение и события

Окно и MLP используют одну физическую геометрию, но разные представления.
Окно показывает графический тайлсет; MLP получает семантический `Frame` без
фона, декораций и HUD. Протокол и датчики используют четыре цвета для
пиксельных признаков, а также отдельный `velocity_x` из физики:

| Индекс | Значение | RGB |
|---|---|---|
| 0 | Пустота | 255,255,255 |
| 1 | Земля / неподвижная преграда | 0,0,0 |
| 2 | Игрок | 0,102,255 |
| 3 | Опасная поверхность | 255,0,0 |

Пиксели идут по строкам сверху вниз. Для RGB in-process доступен `Frame.rgb()`.
Сокет передаёт тот же растр index8 с zlib-сжатием без потерь и нормализованный
`velocity_x` как network-order IEEE-754 float32. MLP не получает `x`, `y`, `vy`,
геометрию карты или готовое расстояние до края. `grounded` и расстояние датчики
извлекают из кадров; `velocity_x` датчик берёт из metadata, без pixel history.

Кадр содержит эпизод, tick, частоты, статус и счётчики приёма команд/событий.
`die`, `success`, `reset` имеют возрастающий `event_sequence`; последнее событие
повторяется в кадрах, поэтому повторный кадр не означает новое событие.
После смерти или успеха **контейнер завершает эпизод и замораживает tick**.
Монитор и сокет продолжают работать; reset начинает следующий эпизод с tick=0.
После смерти/успеха нужен reset, а не команды движения. Это отличие от раннего
прототипа, где часы продолжали идти после смерти.

Физический шаг никогда не растягивается. После паузы ОС контейнер обрабатывает
не более 250 ms догоняющей симуляции, оставшееся время считает в `overrun_ticks`.
Это измеримый пропуск реального времени, а не скрытая замена dt. Будущие датчики
и оркестратор должны учитывать tick, задержки и этот счётчик.

## Проверка

```bash
python -m unittest discover -v
```

Покрыты физические сценарии, две карты, жизненный цикл контейнера,
совпадение геометрии окна и MLP, тайловые карты и слои, оконные события, бинарные команды,
расписание/истечение кнопок, опоздание/дубликаты, частичные TCP-пакеты,
переподключение, reset и непрерывный ход времени, пока контроллер не отвечает.
Также проверяются pixel-сенсоры, observation velocity, архитектура `3-8-2`, изменение весов после
обучения и round-trip checkpoint. Оконные тесты используют SDL dummy и
пропускаются без Pygame.

Game1 не меняется. Оркестратор и более сложные контуры остаются следующим
слоем над MLP-джойстиком и монитором, а не частью физического движка.
