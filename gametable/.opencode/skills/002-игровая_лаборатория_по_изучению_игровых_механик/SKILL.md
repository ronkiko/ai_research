# 002 — Игровая лаборатория по изучению игровых механик

`gamelab_v1` — уже настроенная экспериментальная среда для исследования
игровых механик с помощью обучаемой модели.

По умолчанию лаборатория подключена как отдельный downstream-клиент к тому же GameClient
Host-хабу, что GUI и `game_v1`. Все эти клиенты видят и управляют одной
активной игровой сессией одного игрока. Удобная физическая аналогия: к одному
игровому хабу подключены несколько джойстиков для одного персонажа.

Лаборатория умеет сама выполнить `login` выбранным игроком через общий Host.
Если сессии ещё нет, login создаёт её; если тот же игрок уже активен, Host
безопасно возвращает `reused=true`. Лаборатория не выполняет `logout` и не
заменяет сессию другого активного игрока. Host сериализует команды всех клиентов
в общую монотонную sequence; последняя принятая команда движения становится
активной.

Для воспроизводимых экспериментов TRAIN перед каждым episode и VERIFY перед
каждым run выполняют через Host неразрушающий reset физического состояния
игрока: `x=100`, `vx=0`, `motor_x=0`. При этом игровая session и Host
sequence сохраняются. Обычный лабораторный RUN reset не выполняет и начинает
работу из текущего состояния игрока.

Это описание устройства рабочего места, а не инструкция по выбору способа
решения задачи Директора.

## Текущий физический контроллер

Текущая лабораторная иерархия:

```text
числовая стратегическая цель target_x
        ↓
Spine temporal CNN @ 10 Hz
        ↓
MotorGoal [desired_vx, 0, 0, 0]
        ↓
сертифицированный continuous Motor @ 60 Hz
        ↓
motor_x ∈ [-1,+1]
        ↓
GameServer physics @ 120 Hz
```

Spine видит измеряемое состояние тела и стратегическую цель. Motor не получает
`target_x` напрямую: он получает только локальный MotorGoal от Spine и
proprioception и выдаёт непрерывное actuator effort `motor_x`.

Это техническая спецификация лабораторного инструмента. Она сама по себе не
говорит, когда лабораторию следует использовать и не является стратегией решения
задачи Директора.

## Что умеет лаборатория

Лаборатория через MCP позволяет:

- войти в игру выбранным игроком или присоединиться к уже активной сессии;
- проверить связь с живой игрой и готовность модели;
- получить описание возможностей лаборатории;
- посмотреть метаданные текущего Spine checkpoint;
- посмотреть и изменить reward-настройки;
- запустить обучение модели;
- наблюдать bounded историю и метрики обучения;
- отменить обучение;
- запустить frozen VERIFY;
- наблюдать результаты VERIFY;
- запустить текущую модель в живой игре, задав числовой `target_x` и
  допустимый `tolerance`;
- наблюдать и отменять такой запуск.

Длительные операции асинхронны: стартовый tool возвращается сразу, а ход
эксперимента читается отдельным status tool. Одновременно лаборатория выполняет
только одну активную длительную операцию. Действия TRAIN/VERIFY/RUN и
лабораторные reset-события видны другим подключённым клиентам через общий Host.

## Инструменты лаборатории

Ожидаются MCP tools:

- `gamelab_v1_health`
- `gamelab_v1_login`
- `gamelab_v1_describe`
- `gamelab_v1_model_info`
- `gamelab_v1_reward_get`
- `gamelab_v1_reward_set`
- `gamelab_v1_training_start`
- `gamelab_v1_training_status`
- `gamelab_v1_training_cancel`
- `gamelab_v1_verify_start`
- `gamelab_v1_verify_status`
- `gamelab_v1_verify_cancel`
- `gamelab_v1_run_start`
- `gamelab_v1_run_status`
- `gamelab_v1_run_cancel`
- `gamelab_v1_run_update_goal`
- `gamelab_v1_host_list`

Начинай с `health`. Если нужная игровая сессия ещё не активна, используй
`login`, затем `describe`. Для обычной лабораторной работы не требуется
предварительно входить через `game_v1`.

## GameTable VN: граница лабораторного шага

Это руководство относится только к MODE: LABORATORY. Контракт сцены уже выбран
Roleplay Runtime. Выполни один ограниченный шаг по задаче Директора; верни
наблюдаемые результаты, блокеры и идентификаторы асинхронных операций. Перед
повтором запуска после сбоя сначала прочитай status: предыдущая операция могла
продолжиться. Успешное принятие job не означает успешного завершения.

Статы, память отношений, сердце и голова принадлежат GameTable VN. Не вызывай
старые relationship, character, executive, duality, volition и audience tools;
они не входят в разрешения этого режима. Старые 180-минутная смена, Will/Ego и
Audience не управляют новой Юки. Игровые минуты сцены не ускоряют физическое
время обучения и не создают научные результаты.

## Reward-настройки

Текущий reward-инструмент содержит измеряемые компоненты:

- `distance_progress_scale` — вес уменьшения расстояния до текущей цели;
- `step_cost` — стоимость одного motor-step;
- `success_bonus` — терминальный бонус успешного завершения;
- `timeout_penalty` — терминальный штраф timeout;
- `stopped_near_goal_bonus` — дополнительный сигнал за остановленное состояние
  в заданной окрестности цели;
- `near_goal_radius` — радиус этой окрестности.

Эти параметры являются измеряемой reward-instrumentation для episode reports.
Текущий default `measured_dynamics_policy_search_v1` использует собственный
versioned differentiable training objective, поэтому изменение этих полей само
по себе не меняет его оптимизационную функцию. Не трать экспериментальный бюджет на reward tuning без
machine evidence, что выбранный trainer действительно использует этот параметр.

## Motor и Spine

GameLab больше не создаёт физический Motor внутри Spine TRAIN. Текущий Motor —
отдельный построенный instance с UUID. Для использования под Spine он должен
быть уже обучен и сертифицирован операторским Motor School. Сертифицированный
Motor заморожен и неизменяем; Spine TRAIN не переобучает его.

`model_info` показывает установленные Motor instances в поле `motors`.
Селектор `best` означает лучший установленный совместимый сертифицированный
Motor. Можно передать конкретный `motor_id` UUID. Если нет ни одного
сертифицированного Motor, Spine TRAIN недоступен — это состояние подготовки
лаборатории, а не результат исследования игровой задачи.

Spine checkpoint сохраняет конкретный Motor UUID и hash его frozen brain.
`fresh=true` в `training_start` начинает свежий Spine experiment; он не
создаёт, не сбрасывает и не переобучает Motor.

## Обучение

Обучение, доступное лаборанту через `gamelab_v1`, всегда идёт в realtime через
выбранный GameClient Host и авторитетный GameServer. Это полный training
interface данного рабочего места; скорость мира не ускоряется ради обучения.

Текущий default Spine School использует
`measured_dynamics_policy_search_v1`: измеряет реальные переходы, строит
training-only локальную модель динамики и оптимизирует Spine. Predictor не
управляет персонажем и не является доказательством успеха; физические rollout,
VERIFY и RUN остаются авторитетными.

`training_start` принимает число эпизодов, optional `target_x`, `fresh`,
seed, лимит времени эпизода, `host_id` и optional `motor_id`. По умолчанию
`motor_id=best`, то есть выбирается лучший совместимый сертифицированный Motor.

Если `target_x` не задан, лаборатория сама выбирает цели в поддерживаемом
диапазоне текущего эксперимента.

`training_status` возвращает текущее состояние, количество завершённых
эпизодов, последний результат и bounded `recent_episodes` с reward/loss и
другими метриками.

## VERIFY

`verify_start` запускает frozen-weight проверку текущего Spine checkpoint
вместе с привязанным к нему сертифицированным frozen Motor. Во время VERIFY веса
не обучаются. Успех или неуспех VERIFY — наблюдаемый результат эксперимента, а
не гарантия лаборатории.

## Экспериментальный запуск модели

`run_start` запускает сохранённую иерархию Spine + привязанный certified Motor
в живой игре с заданной поддерживаемой целью. `run_status` показывает наблюдаемое состояние этого запуска.
`run_cancel` останавливает активный запуск.

Для смены цели действующего запуска используй `run_update_goal(target_x)`.
Это сохраняет физическое состояние и историю измерений. Ответ подтверждает
принятую `requested_goal_revision`; в `run_status` проверяй применённую
`goal_revision`. Исходный лимит времени запуска не продлевается.

Статусы `stale`, `unconfirmed` и `contaminated` означают недостаточность
измерений или вмешательство другого клиента, а не доказательство неспособности
модели. Не засчитывай их как самостоятельное решение задачи. Во время чистого
эксперимента не подруливай через `game_v1_move`; мир продолжает работать, а
модель самостоятельно замыкает быстрый цикл управления.

Сохраняй возвращённые `experiment_id` и `policy_id` в исследовательских выводах.
Успешное завершение обучения и наличие checkpoint не означают успешный VERIFY.

Лабораторный MCP не предоставляет лаборанту файловый доступ к реализации
лаборатории. Для обычной исследовательской работы используй инструменты этого
руководства, а не shell-скрипты или исходники соседних директорий.


## Расширенные возможности

Дополнительные Host-инстансы и `host_id` описаны отдельно в руководстве
`003-лаборатория_расширеные_настройки`. Для обычной работы достаточно
default Host. Создание/удаление Host в VN v1 остаётся задачей Оператора.
